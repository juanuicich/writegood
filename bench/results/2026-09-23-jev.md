# Jev against the LLM passes

> Do not ship this method. The code in `bench/scripts/jev/` and the rule
> set `bench/rules/jev-2026-09-23/` find candidates with hand-written English
> word lists, suffix patterns and regexes. That breaks the rule that a pass's
> rule text is its whole definition, and it works only in English. The code
> stays in the repository as a record of this run. The method that follows the
> rule is in `bench/scripts/jev-nolist/` and `2026-09-23-jev-nolist.md`.

TypeSafe's Jev answers one yes/no question per candidate span, with a
probability instead of text. It cannot write a finding: no quote, no note,
no severity in words. This run pairs Jev with code that finds candidate
spans, so Jev only ever answers "is this real", and the code supplies the
quote and a fixed note. Two passes, sentence-openings and one variant of
filler-words, use no model at all.

Rule sets: `bench/rules/jev-2026-09-23/` (the Jev questions and the code
logic, documented pass by pass). Result files: `bench/results/2026-09-23-jev.json`
(nominalization, passive-actor, filler-words, via Jev) and
`bench/results/2026-09-23-code.json` (sentence-openings, filler-words, code
only, no network). LLM baselines: `2026-09-23-R-1.json` and `-R-2.json`
(the app's shipped hybrid pipeline) and the mean of `P-fast-1/2/3.json` (the
fast pipeline). All runs score against the same four drafts and the same
reference.

smoke tests included: under $0.003, against the $5 budget.

## What worked

Filler-words is a strong fit. The candidate list is a fixed word set; Jev's
only job is to say whether removing the word changes the sentence, which is
close to the question's literal wording — no indirection, nothing to count.
It beat every LLM configuration tested, and beat its own code-only variant,
because Jev caught cases the raw word list could not, such as "very" used to
mean "the very first" rather than as an intensifier.

Nominalization did nearly as well as the LLM on F1, at roughly 1% of the
cost and 1% of the wall time. Its false positives were nouns that fit the
regex's syntactic pattern but not the rule's exclusions — see below.

Sentence-openings, run as plain code with no model at all, beat both LLM
configurations on F1. Its "repeated opening" check is exact: comparing the
first two words of consecutive sentences is precisely what the rule asks
for, and needs no judgment call.

## What did not work

Passive-actor's Jev probability does not cleanly separate a real miss from
a decoy near the rule's own boundary. On `draft-essay.md`, "The combination
was forgotten" (the rule's own low-severity case, since the writer is the
obvious actor) scored 0.43; "My bike was stolen" (the rule's own excluded
case, actor unknown) scored 0.42. Lowering the keep threshold from 0.5 to
0.4 recovered the first case and kept the second as a false positive; no
threshold in that range separates them, because the two scores are a
rounding error apart. This is the clearest instance of the documented Jev
weakness with "literal reading over background knowledge": both sentences
have the same surface shape, "was X-ed" with no actor stated, and Jev reads
that shape almost the same way regardless of which fact the missing actor
would be.

Nominalization's candidate code sometimes builds two overlapping spans from
one weak verb ("makes a determination" and, separately, "makes a
determination on each change", because "change" also matched the noun
pattern near the same "makes"). Once the narrower span claims the gold
match, the wider one is a spare false positive. A tighter candidate builder
— one noun claimed per weak verb, nearest first, not near-vs-nearest for
every noun independently — would remove this without touching Jev.

The nominalization candidate code also missed the rule's "standard name of
a thing" exclusion once: "election" (as in "the election, the council has
...") matched the suffix test and Jev said yes, even though a real election
is exactly the exclusion's own example. Background-knowledge exclusions
like this one are where Jev's literal reading shows up; the LLM rule states
the same exclusion but has more context in its own reasoning to lean on.

Sentence-openings' late-subject check, run as plain code, overcounts when a
sentence's subject arrives before the first comma but the comma marks a
later clause. "By February I had come to the realization that the side
streets were the problem, not the hill." has its subject, "I", two words
in, but the code counted all fifteen words up to the comma, because it has
no way to find the true subject — only the nearest comma. This is the
predicted limit from the plan: the run check is exact, the late-subject
check is a comma-position guess.

Jev's answers vary between runs on the same candidate. A second full run
changed "actually" in `draft-essay.md` from excluded (below 0.5) to
included (a false positive against the gold reference). The LLM passes have
the same variance — the README already says to compare means of several
runs, not one — and this run is a single sample for Jev too.

## Recommendation

Replace the LLM for filler-words with the Jev-assisted version. It has the
best F1 of any configuration tested for that pass, at a fraction of the
cost and the wall time, and the failure mode (missing "actually" as a
contrast marker on one run) is rare and low-severity by the rule's own
bands.

Consider replacing the LLM for sentence-openings with the plain-code
version, but only after the late-subject check gets a real fix, not a
threshold tweak — the code cannot tell a short intro clause from a long one
once the true subject sits before the sentence's only comma. The run check
alone is safe to ship as code today; the late-subject check is not.

Nominalization is a plausible replacement once the candidate builder stops
generating overlapping spans from one weak verb and gets a short stoplist
for its worst "standard name" collisions ("election" and similar). As
built, its recall matches the LLM; its precision does not.

Do not replace the LLM for passive-actor. Its F1 is meaningfully lower than
the LLM's, and the specific failure — Jev cannot separate "the writer is
the obvious actor" from "the actor is unknown and irrelevant" when both
read as "was X-ed" with nothing else in the sentence — is a model-level
limit this benchmark's question wording could not route around. A better
prompt might narrow the gap; nothing in the two probes here suggests it
would close it.

None of the four numbers in this report is more than one run (two for
passive-actor's threshold check). `bench/README.md`'s own limit applies
here as much as to the LLM results: treat single-run scores as a first
signal, not a verdict.
